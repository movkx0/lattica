Ranked implementation opportunities

These are implementation recommendations, not measured speedup claims. No new acceleration kernel was implemented for this analysis.

Priority 1 · measured hotspot; proposed optimization

Specialize streaming LDE hashing for the Apple GPU

The reference spent 60.83s in 834 command buffers for lde_absorb.

Implementation: Profile register pressure and integer arithmetic in the fused LDE-to-Poseidon path; prototype one exact-integer specialization and compare layouts without adding host copies.

Validation: Use observed matrix sizes; compare exact outputs, commitments and paths with the CPU oracle, then the existing proof-byte equivalence test. Only a winning component warrants one matched full-proof pair.

Benefit and risk: Halving this kernel time gives an optimistic ceiling of 30.41s (11.8% of reference latency), assuming all savings reach the critical path. This is a projection, not a measured gain. Register spills, occupancy and extra memory traffic can erase the benefit. Effort is medium to high; retain the generic Metal and CPU paths.

src/metal_compute/kernels.metal: lde_absorb; src/block_v2/gpu_hash/engine/lde_execute.rs

Priority 2 · measured hotspot; proposed optimization

Tune the Metal NTT around the actual transform geometry

The reference spent 57.24s in 2,219 command buffers for ntt_tile.

Implementation: Evaluate stage fusion, threadgroup layout and twiddle reuse on the observed sizes. Retain the reference kernel as the fallback; the existing optimized variant is not automatically faster.

Validation: Use observed matrix sizes; compare exact outputs, commitments and paths with the CPU oracle, then the existing proof-byte equivalence test. Only a winning component warrants one matched full-proof pair.

Benefit and risk: Halving this kernel time gives an optimistic ceiling of 28.62s (11.1% of reference latency), assuming all savings reach the critical path. This is a projection, not a measured gain. Register spills, occupancy and extra memory traffic can erase the benefit. Effort is medium to high; retain the generic Metal and CPU paths.

src/metal_compute/kernels.metal: ntt_tile / ntt_tile_cached; src/metal_compute/resident.rs

Priority 3 · measured work amplification; synchronization hypothesis

Reduce fine-grained dispatch and CPU/GPU boundary overhead

The reference issued 19,040 opening command buffers for 0.73s of GPU execution. The resident run spent 267.23s in the quotient interpreter. Command counts, wait intervals and CPU samples are available in the evidence.

Implementation: Start with a component experiment that batches adjacent opening reductions without CPU-visible dependencies. Separately retain CPU quotient evaluation as the control before considering any replacement of the row-wise Metal interpreter. Preserve buffer ownership, dependency ordering and bounded workspaces.

Validation: Check unchanged reduced values, transcript order and proof bytes; verify fewer submissions without extra waits or copied bytes. Treat dispatch batching and quotient placement as separate experiments.

Benefit and risk: No numeric speedup is claimed: queued waits include real GPU work, and host work is not all launch overhead. Removing dependencies incorrectly can corrupt proofs; increasing batching can raise live memory. Effort is medium to high.

src/metal_compute/mod.rs: compute_command / flush; src/block_v2/opening_pcs.rs; src/block_v2/gpu_quotient_prover/metal.rs

Interpretation and limits

  • One instrumented pair, not a statistical performance-promotion experiment. CPU sampling and trace recording add overhead; there were no automatic repeats.
  • The unit is an eight-wallet research aggregation with seven recursive proofs and an independent CPU audit. It is not a full block or accepted-transaction throughput.
  • Host entered-span durations are wall time per thread, not CPU time; inclusive spans, CPU waits and GPU intervals overlap and must not be summed.
  • GPU groups identify expensive work, not an exclusive end-to-end breakdown. Quantitative improvement ceilings are conditional projections, not measured gains.
  • Both configurations use the same unified-memory Mac. Historical Linux figures differ in hardware and implementation and do not isolate a unified-memory architecture effect.
  • Only Command Line Tools were installed: xctrace and the offline metal compiler were unavailable. Existing Metal timestamps and macOS sample were used; no Xcode installation was required.
  • Production Zig/C-ABI paths were inspected, but this fixture profiles the experimental recursive prover. Further production-path measurements are needed before claiming production latency gains.
