CUDA recursive aggregation: profiling and comparison
====================================================

Use the current Plonky3 capacity-128 profile, the same public wallet fixture,
four worker threads, and matching CPU verification binaries for every arm.
The maintained launcher enforces the existing CPU, RAM, scratch, GPU and
teardown limits. Keep the GPU free of other proving jobs during comparisons.

Build each binary separately and copy it before changing feature selections:

  cargo build --offline --locked --release --no-default-features -j1 \
    --features block-v2-wide-lanes,stream,block-v2-capacity-128,gpu-cuda \
    --bin block-v2-paired-probe

The independent CPU binary uses the same features without gpu-cuda. The OpenCL
binary replaces gpu-cuda with gpu. Match the Rust toolchain and RUSTFLAGS.
CUDA requires the pinned NVRTC 12.9 runtime; installing a newer Nsight release
does not replace that requirement.

Experimental features can be measured independently:

  gpu-cuda-batched-submission  Bounded deferred completion waits.
  gpu-cuda-transform-reuse     Shared tables of twiddles and row scaling powers.
  gpu-cuda-quotient-tuning      64-thread quotient evaluation blocks.
  gpu-cuda-lookup-tiling        Up to 16 MiB of bounded lookup tile workspace.
  gpu-cuda-poseidon-diagonal   Exact arithmetic for fixed Poseidon coefficients.
  gpu-cuda-quotient-workspace-large  Up to 256 MiB within the managed allowance.
  gpu-cuda-quotient-tiles-32k   Up to 32k rows and 512 MiB within that allowance.

These features imply gpu-cuda. They do not alter proof parameters, field
semantics, verification, or the maximum managed memory allowance. Keep the
generic feature selection as the control. Architecture-specific performance
claims require measurements on the target GPU; SM70 compilation alone does
not qualify V100 throughput.

Run an uninstrumented comparison from lattica-prover-p3:

  python3 scripts/bench-cuda-recursive.py \
    --output /absolute/path/to/new-evidence-directory \
    --fixture /absolute/path/to/public-capacity-128-fixture \
    --cpu-binary /absolute/path/to/cpu-probe \
    --arm baseline:cuda:/absolute/path/to/cuda-probe \
    --arm candidate:cuda:/absolute/path/to/candidate-probe \
    --gpu-uuid GPU-... --cuda-library-path /absolute/path/to/cuda-12.9.1/lib

The default is one warmup per arm and size, followed by five repetitions with
alternating arm order, for four and eight inputs. Every recursive proof and
root is CPU-audited outside the timing interval. Source/binary fingerprints,
per-run commands, telemetry, resource accounting and retirement receipts are
saved with the results. The controller itself should run in a bounded user
service when used for long campaigns.

  python3 scripts/report-cuda-comparison.py /path/to/evidence/result.json \
    --baseline baseline --candidate candidate --output /path/to/comparison.json

Promotion requires at least 2% lower median proof-interval latency on an
improving workload with at least 80% paired wins, and no workload median
regression over 2% in either launcher or proof-interval time. Repeat an
inconclusive comparison once. Reports reject incomplete, instrumented,
unaudited, resource-failing, duplicate or unmatched samples.

Four inputs contain three user transactions and one issuance entry; eight
contain six user transactions and two issuance entries. Reported user rates
are aggregation equivalents, excluding wallet generation, native/durable
application and the separate CPU audits.

Nsight diagnostics
------------------

Build the optional annotation helper against the installed Nsight NVTX SDK:

  cc -O2 -shared -fPIC -I/usr/lib/nsight-systems/target-linux-x64/nvtx/include \
    scripts/linux_profile_clock.c -o /absolute/path/to/nvtx.so -ldl

Create a profiling assignment (all artifact paths must be absolute):

  {"tool":"nsys","executable":"/usr/bin/nsys",
   "nvtx_library":"/absolute/path/to/nvtx.so"}

Use a separate fresh output directory and one CUDA arm, adding:

  --linux-profile /absolute/path/to/profile.json --repetitions 1 --warmups 0

This enables CUDA/NVTX/OS-runtime tracing, without hardware counters or CPU
sampling. The shared worker still authenticates its own executable, arguments,
PID, invocation and cgroup. A pinned helper transfers the service MainPID to
the prover before exec; ExitType=cgroup retains the profiler until export
finishes. The same memory limits and whole-cgroup cleanup remain in force.
Unrelated environment variables are removed before launching Nsight.

CUDA annotations contain static stage names and public program dimensions;
they do not record witness contents, random seeds or challenges. Normal runs
do not load the NVTX helper. Profiling results are marked instrumented and
cannot be included in throughput comparisons.

  nsys export --type sqlite --output /path/to/trace.sqlite /path/to/nsight.nsys-rep
  python3 scripts/analyze-cuda-profile.py /path/to/trace.sqlite \
    --output /path/to/profile-analysis.json

The analysis separates kernel-active time, kernel geometry, CUDA API times
and inclusive NVTX host ranges. Waits overlap GPU execution; nested host
ranges must not be summed into a wall-time breakdown.

Nsight Compute assignments use tool=ncu, executable and nvtx_library plus
kernel, launch_skip, launch_count (1..8), and an explicit metrics list. For
example, sass__inst_executed_per_opcode provides instruction diagnostics on
supported tools/devices without broad counter collection. Clock and cache
control are disabled. Capture only a few representative launches; avoid
replaying every kernel of a recursive proof.

Hardware counters may require administrator access. The launcher does not
change global driver or perf permissions. If access is restricted, record
unavailable metrics; a host administrator can enable NVIDIA profiling access
before retrying. Nsight Compute
2026.3 does not support Volta; use a compatible older release for a V100.
Managed Nsight Compute captures follow the worker helper's exec handoff within
the assigned cgroup. Standalone captures target only the application.
The completion check accepts .ncu-rep and the .ncu-repz compressed format used
by Nsight Compute 2026.3. Missing, empty or ambiguous reports fail the run.
Inspect either format with ncu --import /path/to/report --page raw --csv.

Validation
----------

Enable block-v2 when compiling CUDA tests: primitive-only builds omit lookup
and witness coverage. The recursive benchmark builds already include it.
Run ignored GPU tests serially with an explicit LATTICA_GPU_DEVICE_UUID and
the pinned CUDA library path. Test asynchronous-error cases in separate
processes, since they intentionally invalidate the CUDA context.

Run Compute Sanitizer memcheck, racecheck and synccheck on changed modules,
including the CPU-oracle transform, lookup and quotient tests. Compile checks
cover Volta and Blackwell. Full recursive benchmarks remain the acceptance
test; a passing primitive suite or faster microbenchmark alone is insufficient.

The opt-in cuda_transform_reuse_benchmark test uses public synthetic matrices,
checks each result against a CPU DFT outside timing, and reports warmup and
measured rows when LATTICA_CUDA_TRANSFORM_BENCHMARK=1. Its timings include
device allocation and transform execution, and are not transaction throughput.

Quotient workspace follow-up (2026-10-30)
---------------------------------------

Add gpu-cuda-quotient-workspace-large to the previously qualified four tuning
features. It raises the quotient's internal workspace cap from 64 to 256 MiB,
allowing the measured workload to use 16,384-row tiles instead of 4,096 rows.
The planner still checks remaining managed memory and each allocation limit.
The worker retains its 7 GiB managed allowance, 4 GiB context allowance and
1 GiB headroom; both CUDA arms still peak at 6.94 GiB of managed memory.

One warmup per arm and size, followed by five alternating repetitions:

  Entries  Previous tuned CUDA  Larger workspace  OpenCL control
        4              35.432 s          31.042 s        30.097 s
        8              66.896 s          58.384 s        57.402 s

These are median proof-observation intervals, including root promotion.
The candidate wins all ten CUDA pairs and reduces the medians by 12.39% and
12.72%. Whole-launcher medians fall from 41.873 to 37.265 seconds and from
73.964 to 65.247 seconds. All 216 proofs and 36 roots, including warmups and
OpenCL controls, pass independent CPU verification. Use these fresh controls;
absolute timings differ from earlier sessions with the same baseline binary.

Median quotient device time falls from 7.437 to 3.141 seconds for four entries
and from 14.684 to 6.257 seconds for eight. Quotient device calls per proof fall
from 2,057 to 521. Separate Nsight captures confirm a 64-to-256 block grid with
64 threads per block; sampled occupancy rises from 4.17% to 12.70%. Both use
54 registers per thread and show zero measured local-memory traffic. These
single-launch diagnostics are excluded from the performance comparison.
All eight profiled proofs and two roots also pass CPU verification.

Clocks were not locked. The GPU changed from P1 with a reported 14,801 MHz
memory clock to P0/15,001 MHz before four-entry repetition three; all three arms within each round
shared the observed state and memory clock. Every sample is retained. The
runner now records memory clock and power state in its existing telemetry query.

Transform follow-up (2026-10-30)
------------------------------

The existing 32k-tile configuration remains recommended. Static NTT
specialization plus shared twiddle tables passed correctness checks but missed
the 2% adoption threshold. No experimental transform code was integrated.

One warmup per arm and size, then five alternating measured repetitions on the
desktop RTX 5080 produced these median proof-observation intervals:

  Entries  Qualified CUDA  Transform candidate  OpenCL control
        4        29.824 s             29.475 s        30.184 s
        8        56.288 s             55.688 s        57.777 s

The candidate wins all ten proof pairs, reducing the medians by 1.17% and 1.07%.
Every paired proof reduction is below 2%; no repeat is recommended. Whole-launcher
CUDA medians fall from 36.263 to 35.711 seconds and from 63.299 to 62.848 seconds.
OpenCL launcher medians are 35.662 and 64.149 seconds. All 216 proofs and 36 roots,
including warmups, pass independent CPU verification with no memory-limit events.

Transform device-time medians fall from 4.545 to 4.259 seconds and from 9.201 to
8.628 seconds. This local gain has limited impact on the full proof interval.
Both CUDA arms peak at the same 6.94 GiB of managed memory under the existing
7 GiB allowance. Host, GPU, thread and zero-swap limits remain unchanged.
Active GPU samples share P1 and 14,801 MHz memory clocks; clocks were not locked.
All samples and raw telemetry are retained, with no failed telemetry queries.

Validation includes 206 CUDA core checks for the static variant, six combined
transform checks, and five baseline transform checks. Each experimental variant
also passes six checks under each of memcheck, racecheck and synccheck, with no

qualification is limited to the desktop RTX 5080.

All 840 opening main source hashes remain unchanged, and all 19 owned services

These capacity-128 measurements include aggregation and root promotion of retained

This shared host change needs no additional feature flag; use the integrated
transform configuration above.
