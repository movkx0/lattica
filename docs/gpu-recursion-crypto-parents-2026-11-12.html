Shared AES/SHAKE parent pipeline

Implemented November 12; validated November 13, 2026 · Default typed workflow · Base commit 188dabb

Two complete SHAKE requests finished in 55.27 seconds instead of 65.06: 15.0% less time. Both configurations generated and independently verified twelve fresh recursive proofs with identical proof geometry. Preprocessing misses fell from 12 to 6. Both release builds and 56 focused checks passed.

The previous scheduler compiled and prepared each request's parents serially on the GPU-owning thread. The new default shares one bounded queue across requests and transactions, allowing parent compilation and lowering to overlap the preceding GPU proof. Matching positions share the existing exact-identity preprocessing cache.

The pending graph-parent comparison also passed: 82.34 → 70.61 seconds, 14.2% less time, with the same eighteen recursive proofs.

Implementation

  • The full AES/SHAKE workflow shares one bounded parent preparation window across requests and transactions, visiting matching positions before advancing levels.
  • Workers own each child set exactly once, compile the parent, reject reordered children, and drop the child proofs before template lowering.
  • The single GPU consumer uses the existing exact-identity preprocessing cache and releases the preparation permit after source retirement so the next parent can prepare during GPU execution.
  • Every completed parent is verified against its own request contract and endpoint context. Full-workflow proof counts and reduction fan-in are unchanged.
  • The archive request profiler now uses this production parent queue and schedules matching native groups across repetitions, reporting pipeline completion separately from overlapping per-request latency.
  • The graph and crypto schedulers share the tested position-order iterator. All compiler, AIR, cryptographic parameter and GPU-kernel sources are unchanged.

Scope

  • One matched component measurement per revision on this GPU. No confidence interval or new full N3/N4 workflow speedup is claimed.
  • The SHAKE comparison repeats one archived ten-component request twice at group width 2, generating and verifying twelve fresh recursive proofs. The full workflow uses the same parent queue, but the comparison does not contain two distinct transactions.
  • The N4 default native width is already 16. This comparison isolates a multi-parent workload; it does not imply a parent-pipeline gain for requests that fit in one native group.
  • The baseline stage total sums two sequential sample times; the candidate uses its whole pipeline makespan. The controller times are also reported for a common outer timing boundary. Candidate per-request latencies overlap and must not be summed.
  • The graph comparison uses the r119 pipeline source before the crypto extension. r120 moves its pure parent-order iterator into the shared weighted module; focused ordering checks cover that move.
  • Compiler, AIR, security parameters, proof counts, native group widths, GPU kernels and memory limits are unchanged in the matched request comparison.
  • CPU reference checks and all measured recursive proofs passed independent verification and mutation checks. No security audit, fresh transaction generation, macOS or CUDA qualification was performed.
