Ranked implementation opportunities

Priority 1 · Medium effort

Optimize exact Metal squaring and the Poseidon S-box

Strong hotspot evidence; speedup unmeasured

Evidence. Leaf/sponge hashing takes 57.55s and tree compression 3.05s: 82.3% of recorded GPU kernel intervals. The latest full candidate still selects the reference multiplication/loop variant. LATTICA_OPTIMIZED currently changes both multiplication and permutation unrolling.

Next change. Separate multiplication strategy from permutation unrolling. Add an exact Goldilocks square that reuses symmetric cross-products, then apply it to the two squarings in x^7. Screen looped and selectively unrolled versions on the largest actual sponge shape. Inspect compiler output and register pressure before selecting a workgroup size.

Each width-8 permutation executes 86 S-boxes; the current x^7 chain uses two squares and two other field multiplications per S-box. That exposes 172 squarings per permutation. A limb-specialized square may reduce arithmetic, but this source count is not a speedup estimate. Exact Metal integer compute is already integrated and proof-qualified.

Acceptance gate. Check full-width and noncanonical inputs against the CPU/u128 oracle, Poseidon known answers, partial columns, commitment equality and fixed-seed proof bytes. Reject a variant that only improves isolated multiplication while slowing the sponge.

Priority 2 · Medium to high effort

Carry shared buffers through LDE, CPU quotient and openings

Strong traffic evidence; full hybrid latency unmeasured

Evidence. The winning configuration still records 250.09 GB of explicit host copies, 154.62 GB of host reordering, 14.35s in decode counters and 3.72s in LDE reordering. The readback implementation allocates a second matrix for multiple column bands. These counters overlap and must not be added into a predicted saving.

Next change. Build on the implemented resident-storage/CPU-quotient split. Give opening inputs an owned Metal-buffer view with stride and offset metadata, alongside the CPU slice view. Let GPU consumers read canonical retained storage directly. Use per-buffer completion and a small reusable ring where CPU preparation can overlap independent GPU work.

PrefixStorage already borrows canonical FrozenWords as field elements, but OpeningMatrix exposes only a CPU slice and downstream paths still marshal values. SharedWords CPU access currently drains the whole queue. Shared memory makes common ownership practical; it does not remove hazards, layout conversion, or DRAM traffic. Apply the smallest necessary synchronization scope. Apple synchronization guidance.

Acceptance gate. Keep quotient=cpu when isolating resident storage. Verify row/column order, tails, canonical representation, lifetime and failure cleanup. Measure complete commit/opening latency and peak RSS, not only copied bytes. Prefix fusion alone showed no clear benefit and should remain experimental.

Priority 3 · High effort

Replace quotient temporary traffic before expanding GPU use

Clear implementation issue; end-to-end benefit unknown

Evidence. Base/extension temporary typing is implemented and reduced the small correctness circuit from 20,778 to 8,760 words (57.8%). The compiler still allocates a persistent temporary for every non-leaf expression it encounters. The historical full-size resident path was slower and is not evidence for the newly typed version.

Next change. Count expression uses, keep single-use values on the evaluation stack, assign reusable slots by last use, and preserve separate base/extension widths. Then evaluate block-specialized or generated AIR kernels if the interpreter remains expensive. Pass challenges and public values at runtime and key reusable plans by the exact AIR/program identity.

The remaining obstacle is execution structure and scratch traffic, not merely finding another Apple API. Exact GPU arithmetic can work, but a giant interpreted expression program with long-lived global temporaries is a poor starting point. Do not restore the old hard resident-worker memory budget as a workaround.

Acceptance gate. Compare complete quotient vectors and full proof bytes against CPU on the same transcript. Record live temporary words, instruction counts, rows per tile and full component time including marshalling. Keep CPU quotient as the default for measured candidates until a GPU component wins.

Priority 4 · Small measurement fix; medium kernel work effort

Requalify SME on a whole CPU kernel

Hardware qualified previously; performance unresolved

Evidence. The existing optional SME component uses streaming SVE and reported eight u64 lanes; it does not use the ZA matrix accumulator. Its timing includes canonicalization while the Plonky3 comparator canonicalizes after timing. The previous 0.611 versus 0.514 ns/element comparison cannot establish an intrinsic ISA advantage or disadvantage.

Next change. First give both implementations the same canonical or redundant-output contract. If competitive, prototype an entire Poseidon batch or a suitable quotient arithmetic block so streaming transitions, loads, stores and normalization are amortized. Compare with the existing optimized AArch64 Plonky3 path, using runtime feature detection and the CPU fallback.

A small out-of-line multiply call is unlikely to establish the best use of SME. Apple documents SVE access through streaming mode on current SME implementations; SME support does not imply ordinary non-streaming SVE support. Plonky3 already has an AArch64 packed backend, whose two-lane multiplication uses interleaved scalar mul/umulh assembly. Apple XNU SME documentation.

Acceptance gate. Use equal work and output contracts, include streaming/ABI overhead, check all arithmetic boundaries, and only pursue integration if a real CPU component improves. Do not infer an 18-thread gain from a one-thread array multiply.

Priority 5 · Low to medium effort

Tune transform geometry and command scheduling narrowly

Secondary opportunity

Evidence. Cached transforms reduced the large component NTT interval by 75.1%. The full candidate now records 12.11s of LDE transform time. Its table cache has 849 hits, 19 misses and no evictions. Opening reduction records 19,040 tiles and 7.49s complete opening time, but only 0.73s in its direct reduction kernel counter; related NTT work is counted elsewhere.

Next change. Use the existing 10/11/12 tile-log controls on one representative shape. Consider separate hash and transform workgroup settings. Batch compatible dispatches only where dependencies permit, and quantify encode/submit/wait cost before a Metal 4 migration.

The 43,755 kernel calls make scheduling worth inspecting, but the measured opening enqueue counter is only 0.089s and shader compilation is about 0.096s. Thousands of calls alone do not establish large CPU encoding overhead. Increasing the twiddle cache above 256 MiB has no eviction evidence in this run. Metal 4 capabilities.

Acceptance gate. Keep field arithmetic, storage and quotient selection fixed. Compare component wall time, total command intervals, synchronization and memory; preserve transcript ordering and error propagation.

Priority 6 · Low to medium effort

Audit native Zig hashing separately from research proving

Source opportunity; production hotspot not measured

Evidence. Zig field.mul expresses u128 multiplication followed by remainder; its Poseidon S-box calls generic pow(x, 7), and the internal diagonal still uses general field multiplication. The recent Metal changes do not accelerate these functions or activate Metal in the production C ABI.

Next change. Inspect optimized AArch64 code before assuming remainder is expensive. If profiles justify it, use an explicit four-product x^7 chain, the proven fixed-diagonal identities and exact Goldilocks reduction, with native mul/umulh or compiler-generated equivalents. Batch independent Merkle hashes only when the caller has enough work.

This is the practical CPU route for wallet/node hashing. Tiny individual hashes are poor GPU-offload candidates, and a compiler may already specialize constant arithmetic. Existing Rust session preprocessing caches also mean that simply proposing a new generic cache is not enough.

Acceptance gate. Preserve canonical outputs, known-answer vectors, byte-for-byte Rust/Zig agreement and node acceptance behavior. Measure a production caller separately; do not apply the research aggregation speedup to wallet transactions.

A minimal validation sequence

  1. One isolated change: begin with the square/S-box work, holding NTT caching, storage, quotient backend and thread count fixed.
  2. Relevant correctness checks: arithmetic boundaries and randomized cases, commitment/proof-byte equivalence and an independent CPU verifier.
  3. One real hotspot shape plus one tail case: one warm-up and three short samples, including preparation and synchronization. Do not generate a full cross-product of thread counts and knobs.
  4. Only a clear component winner earns a full comparison: one fresh reference and one candidate aggregation, 18 threads, seven proofs and a CPU audit each. Reuse the current result for screening context, not as an indefinitely valid reference. Repeat only for a marginal or unstable result.

No new benchmarks ran during this review. No global execution timeout, RSS cap or hard resident-worker budget was introduced.
