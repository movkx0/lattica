Architecture and default behavior

  • Direct typed verification of up to sixteen unchanged native AES segments in one recursive proof, eliminating intermediate singleton and binary wrappers.
  • Exact descriptor/index/family binding, contiguous span checks, shared input commitment constraints, adjacent endpoint constraints, and complete request start/output bindings.
  • AES roots join the global weighted CPU preparation queue and the one-entry exact-template public GPU preprocessing cache.
  • Constrained typed AES adapters for graph leaves and Alpha uniform/sparse producer branches, preserving existing public legacy APIs and final aggregate format.
  • Read-only archive benchmark support for AES, with a fresh-proof reference using the production MachineAir CPU lookahead pipeline.

N4 planning

The same 536 native components require 239 recursive proofs instead of 319, excluding auxiliary branches: 80 fewer (25.1%). AES request proofs fall from 100 to 20 across four transactions. Graph/final reductions remain unchanged. These counts do not establish a full N4 runtime improvement.

Validation and resources

30 targeted Rust tests and 71 Python tests passed; the CPU-only research configuration compiled. AES tests cover descriptor/index/context/root substitutions, invalid segment coverage, and complete request endpoint constraints. Actual GPU proofs reject changed public statements, and reordered native segments are rejected.

The RTX 5080 used a 10.5 GiB managed GPU allowance in both runs. The typed run observed 6.48 GiB process GPU memory and 3.28 GiB cgroup memory peak. These are observations for this request, not workload-wide memory bounds. Both guards confirmed unchanged source inputs and clean process/GPU teardown.

Measurement scope

  • Timing covers recursive aggregation of one five-segment AES request (request 4, transaction 0). Native AES proof generation is excluded; reimport, verification, compilation and recursive proof generation are included.
  • Native AES inputs were absent from the older SHAKE archive. Five native proofs were generated once from exactly the same deterministic N4 inputs in a separate bundle; both recursive paths revalidate identical files.
  • Both paths use the same source revision, GPU, 10.5 GiB managed GPU allowance and 36 GiB worker envelope. The machine reference uses the existing production CPU lookahead with the wide-memory policy (two ready jobs, 34 GiB reservation); typed batching uses the typed-batch policy (36 GiB reservation).
  • The reference uses the same bounded native compiler as the candidate. Its outer proof execution and binary reduction use the existing MachineAir pipeline. This is a matched request comparison, not a rerun of the full earlier workflow.
  • Warm median is the median of samples 2 and 3. The typed path retains one exact-template public preprocessing entry between samples; every recursive proof is freshly generated and independently CPU verified.
  • Full N3/N4 aggregation, graph/Alpha consumer proof execution with these request roots, and transaction generation were not timed in this pass. Proof-count savings are planning results and do not establish a whole-workflow speedup.
