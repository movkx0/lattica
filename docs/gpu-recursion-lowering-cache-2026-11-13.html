Recursive aggregation: measured optimization candidates

13 November 2026 · both candidates rejected for insufficient completion-time improvement; existing defaults restored.

The second prototype reuses immutable lowering metadata for identical verifier programs before GPU preparation. Every proof still creates its own witness and randomness. Exact program identity, verifier registry, and proof profile govern reuse.

These times include CPU preparation, GPU proving, and independent CPU verification for all recursive proofs in each workload. They exclude archive revalidation and process startup. Samples share the existing archived fixture; this is not a new full RingCT transaction benchmark.

CPU template preparation fell from 13.84 to 12.03 seconds on the graph workload and from 11.32 to 10.35 seconds on SHAKE. Whole-workload changes remained below 1%. Much of the saved CPU work was already overlapped with GPU proving; neither result establishes a material completion-time gain.

Prototype design and correctness

  • Cache immutable lowering metadata by the existing exact program/registry/profile identity.
  • Retain no Program, witness values, proof randomness, or GPU allocation. Rebind to the current independently constructed Program on every hit.
  • Permit independent cache misses to compile concurrently; synchronize only metadata lookup/replacement.
  • Reserve at most 256 MiB within the existing weighted preparation capacity, reducing job capacity by that reservation. Tight windows disable retention without rejecting their largest job.
  • Release each cache at the end of its preparation window, before reducing the next tree level.
  • Proof layout, cryptographic parameters, public binding, ordering, and CPU verification remain unchanged.

The checks cover exact identity matching, changed programs and registries, fresh source ownership, concurrent replacement, oversized metadata, exact memory admission, fused reduction constraints, and rejected witness/public/order mutations. Every recursive proof in both comparisons passed independent CPU verification.

Candidate rejected after measurement

A GPU row-factor lookup table made the large scaling kernel faster, but graph completion was 70.61 to 70.04 seconds and SHAKE completion was 55.27 to 55.46 seconds. That candidate was removed from active code; its patch and measurements are preserved.

Next architectural target

The remaining exposed path is GPU proof execution plus the first parent preparation. A follow-up should prioritize reducing the GPU work per proof or preparing the first parent earlier with exact verifier and witness binding. Reuse that only saves CPU work already hidden by GPU execution is unlikely to move completion time.

Scope

  • Matched archived input fixtures with newly generated recursive proofs; not a fresh complete RingCT transaction workflow.
  • Graph workload repeats one eight-leaf subtree twice; SHAKE workload repeats one ten-component request twice with group width two.
  • Single matched measurements are not confidence intervals.
  • Graph baseline r119 predates moving the same parent iterator into a shared helper in r120. SHAKE baseline r120 is the immediate predecessor.
  • OpenCL NVIDIA GPU qualification only; no new CUDA or Apple qualification.
