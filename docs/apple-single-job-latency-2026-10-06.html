Single-job latency and memory

Apple M5 Pro · 18 CPU cores · 64 GB unified memory · macOS 27.2. One eight-transaction aggregation job per profile, using native Metal acceleration and one 18-thread worker.

Both compact profiles completed and passed independent CPU audits.

Direct readback took 211.84 seconds versus 214.36 seconds for the compact baseline: an observed 1.18% latency reduction. One pair is insufficient to establish a repeatable speedup. These results do not trigger a default or production promotion.

Why the earlier runs stopped

The profiles retaining full expanded host matrices stopped during their first proof when macOS reported elevated memory pressure. Neither produced a completed job. They reported no proof-verification or GPU arithmetic failure before stopping.

Controls and correctness

Both completed profiles used shared Metal buffers, specialized Poseidon, cached NTT tables, CPU quotient evaluation, compact prover data, and GPU query gathering. The paired profiles differed only in direct LDE readback. Opening-denominator caching was disabled. Each arm used a fresh process and the same pinned wallet-proof fixture.

The merged code passed 22 focused tests, including field arithmetic, Poseidon, NTT/LDE output, query reconstruction, unwind cleanup, and full proof-byte equivalence with both readback layouts and query gathering. A Metal allocation-planning issue found during qualification was fixed by reserving space for the backend-owned NTT table cache before selecting a query tile.

Timing includes worker startup, aggregation, and independent CPU audit. Builds and wallet-proof generation are excluded. RSS is sampled process residency, not a measurement of total physical footprint; GPU memory overlaps process/unified memory and must not be added again. No fixed worker RSS ceiling or total benchmark timeout was used; OS memory-pressure monitoring remained active.
