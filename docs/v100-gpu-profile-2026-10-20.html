Shared twiddle factors in the GPU prover

Sharing transform factors reduced median aggregation time by 2.81–3.75% across the three tested workloads. Native wallet proving had mixed paired results and a 2.47% slower median. The selected implementation shares butterfly factors within each workgroup, with measured shape restrictions and explicit local-memory admission.

The previous campaign and its evidence remain preserved. Its RNG batching, field arithmetic, guarded Poseidon2 diagonal and witness fusion are part of this campaign's baseline.

What the fresh profiles showed

The initial eight-input profile recorded 15.57 seconds in LDE transforms and 15.31 seconds in row hashing. The four-input profile recorded 7.22 and 7.83 seconds respectively. Transforms already combine several FFT stages per launch; repeated field multiplication inside each tile was the next target.

In the matched warmed four-input profiles, recorded transform event time changed from 7.2180 to 6.2830 seconds. This is a diagnostic kernel comparison, separate from the complete-prover qualification above.

The eight-input profiles recorded 15.5694 seconds in LDE transforms before the change and 13.4939 seconds after it. The selected four-input profile still spent 7.8260 seconds in LDE row hashing and 3.0140 seconds in quotient kernels. These remain candidates for future profiling; this campaign does not claim improvements in those kernels.

Experiments and the selected implementation

A number-theoretic transform (NTT) is the finite-field counterpart of an FFT. Its butterfly steps combine pairs of values using known field multipliers, commonly called twiddle factors. Reusing those public factors changes the execution cost while preserving the transform's mathematical result.

The component screen compared ordinary powers, reuse of the public root squaring chain, shared row-scale powers, skipping identity factors, and sharing complete butterfly factors across columns. Independent Python-integer transforms checked forward/inverse operations, coset scaling, output ordering, irregular widths, in-place stages and memory fallback. Small cases were also checked against the direct DFT sum. All seventy variant/oracle cases passed; the small-shape extension repeated these checks.

The selected kernel computes each stage's butterfly factor once per workgroup and shares it across columns and repeated row blocks. It also reuses the root squaring chain and the row-scale origin/step calculation. This adds a half-tile of local words and one barrier per FFT stage. The host checks the complete requirement against the existing local-memory allowance, capped at 48 KiB after static usage. When that layout does not fit, the original cached and uncached kernels remain available.

Previously, each butterfly multiplied an outer root factor by an inner power and then multiplied the data by that result. The first product repeats across columns and row blocks. The shared kernel forms those products once, synchronizes the workgroup, and reuses them while retaining the existing data multiplication. No transform stages or global buffers are added.

Small transforms showed synchronization overhead. Default selection therefore requires the measured V100 and either at least 16,384 rows with 16 or more columns, or at least 262,144 rows with 3 or more columns. Explicit reference/research selections retain their controls. Legacy DFT programs retain their existing kernel and memory plan. The broad all-shape build is preserved as an experiment and was superseded before proof qualification.

Correctness and resources

The final source passed 35 targeted tests: 16 host tests and 19 GPU tests. They cover local-memory boundaries, shared/reference transform dispatch, full CPU/GPU transform parity, scaling and ordering, coefficient guards, arithmetic, commitments, witness scheduling and rejection, cleanup, and native wallet proofs verified after GPU shutdown. CPU-only and GPU-without-tuning compile checks also passed. This does not claim the entire repository test suite passed.

The benchmark ledger contains 108 independently CPU-audited outputs, representing 400 fresh benchmark proofs. All audits passed and output proof hashes are unique. Native wallet audits also reject changed public statement bytes. Required GPU stage counts remain sixteen for recursive proofs and fifteen for native wallet proofs.

The existing managed-memory admission, driver reserve, host limits, zero-swap checks and 250 W power limit are preserved. The optimization changes workgroup-local scratch use; it adds no managed global buffer. Sampled NVML peaks can miss short-lived allocations, particularly for subsecond wallet runs, and are not used to claim a memory reduction.

How the GPU proving process works

1. Admit and compile public metadata
The CPU checks budgets and builds AIR, witness schedules and public program/layout data.
2. Construct the witness
GPU kernels derive public values and fill the trace. Dependency waves and status checks enforce execution order.
3. Hide and extend
Fresh randomness supplies salts and masks. Inverse transforms interpolate coefficients; shifts, padding and forward transforms form the low-degree extension.
4. Commit and challenge
Poseidon2 hashes rows and builds Merkle trees. Transcript operations derive challenges; GPU lookups run where the proof profile requires them.
5. Evaluate constraints
The host compiles public quotient code. GPU specialized or interpreted evaluation combines constraints and constructs quotient commitments.
6. Open and run FRI
GPU kernels form opening polynomials, fold FRI layers, grind nonces and gather query/authentication data.
7. Serialize and verify
Bounded proof material returns to the host for serialization. This campaign independently verifies every output with the unchanged CPU verifier.

Transforms, hashing and transcript operations recur throughout proving. Public programs and compiled code can be reused; private witness buffers, masks, salts and scratch belong to one attempt. The legacy wallet profile uses quadratic extension challenges and 96 FRI queries; recursive proofs use cubic challenges and 128 queries. Both retain hiding, 16-fold LDE blowup and 16 query-grinding bits. The optimization changes execution, not these proof parameters.

Four existing wallet inputs produce two wrappers and one merge: three fresh recursive proofs. Eight inputs produce four wrappers and three merges: seven proofs. See the maintained GPU proving guide for the stage inventory and backend details.
