What was measured

Every trial proves an eight-wallet, level-three subtree: four paired wrappers followed by three merges. The timer is the sum of the wrapper-command and merge-command timers. Wallet fixture generation, preprocessing-key registration and the independent final audit are outside this timing boundary, matching the archived Linux benchmark.

9 Mac roots passed independent CPU verification from a root-only bundle after inner proofs were removed. Each completed trial performed seven fresh recursive proofs; no previously completed node was resumed. This workload does not qualify a 64-transaction full block or measure end-to-end delivered-transaction throughput.

Controls, run order and workload matching
  • The 16-thread Mac series ran first. The remaining 8- and 24-thread trials then ran sequentially in the order 8, 24, 24, 8, 8, 24. The overall completed run order is 16 → 16 → 16 → 8 → 24 → 24 → 8 → 8 → 24. Heavy benchmark processes did not overlap.
  • All Mac thread settings reused exactly the same eight wallet-proof files. The original randomized Linux wallet-proof bytes were unavailable locally, so new Mac fixtures were generated. All three registration-key digests, the height digest and the expected external public statement matched the Linux pins.
  • Linux controls were interleaved on October 2; the Mac was measured on October 3. These are cross-system exploratory samples, not randomized paired measurements between hosts. Three samples per setting are insufficient for a strong statistical or causal claim. First runs remain in the reported data.
  • The Mac did not enforce an exclusive-host or fixed-frequency policy. Power and thermal-status observations are included in the evidence, but they were not monitored continuously.
  • Twenty-four Rayon threads oversubscribe the Mac’s 18 physical cores. Identical thread settings do not imply identical CPU utilization across backends.
  • The preserved Linux ram16-control was also GPU-enabled. Its three times were 431.246, 385.167, 385.982 seconds (median 385.982 seconds). It checks the default-feature change; it is not a Linux CPU-only baseline.

What this says about unified memory

This measures the complete systems and their selected backends. The M5 Pro result demonstrates CPU proving performance on an Apple Silicon system. It does not isolate a speedup caused by unified memory, because the Mac GPU was unused and the Linux run offloaded work to a discrete GPU.

Architectural context

Apple’s unified-memory design lets the CPU and GPU share system memory. Apple advertises up to 307 GB/s of memory bandwidth for the M5 Pro; this is a vendor specification, not bandwidth measured by this benchmark. Apple Metal documentation; Apple M5 Pro specifications.

Discrete GPU programs can pay for transfers between host and device memory. NVIDIA recommends reducing those transfers and keeping intermediate data on the GPU. The Linux backend already applies resident processing to reduce transfer costs. NVIDIA guidance on host/device transfers.

Evidence needed to isolate the benefit

A future Metal implementation could test whether shared CPU/GPU buffers reduce transfer costs for this workload. That is a hypothesis, not a result from this run.

A controlled follow-up should hold proof parameters and algorithms fixed, compare CPU-only implementations on both hosts, and compare explicit-copy versus shared-buffer paths on the same Apple GPU. Transfer bytes, transfer time, memory bandwidth, energy and end-to-end proof time should be measured together.

The current experiment did not measure DRAM bandwidth, PCIe traffic, power consumption or GPU memory use. Avoid attributing the elapsed-time difference to a single hardware feature.

Memory and execution conditions

The largest observed Mac worker RSS was 42.47 GiB. Scratch used anonymous memory mappings with a 34 GiB mapped-allocation cap and a sampled 44 GiB worker RSS stop threshold. This small allocator adaptation replaced Linux tmpfs-backed mappings while keeping the proving parameters unchanged; its four allocator tests passed.

These memory counters have different accounting semantics and should not be interpreted as a like-for-like RAM-efficiency comparison. Mapped scratch overlaps worker memory; do not add the two. GPU VRAM is not included in these figures.

Linux enforced a 44 GiB worker cgroup limit, a 34 GiB spill-allocation limit and zero worker swap. macOS used an allocator cap and an external RSS watchdog, which do not enforce Linux’s no-swap policy. System swap was in use at an observation during the first run; no pre-benchmark swap baseline or per-worker swap accounting was captured. The recorded observation cannot establish whether benchmark pages were swapped.

The current bounded GPU worker requires Linux cgroups. The Mac comparison therefore used the native CPU executable. No GPU safety check was bypassed.

Build and execution commands

Run from the archived v3 lattica-prover-p3 directory, using the local Rust 1.96.0 toolchain:

RUSTFLAGS='-C target-cpu=native' cargo build --offline --locked --release \
  --no-default-features --features block-v2-wide-lanes,stream \
  --bin block-v2-grouped-probe \
  --bin block-v2-grouped-artifact-audit \
  --bin block-v2-grouped-publics

The comparison controller freezes the Linux public-statement pins and resource thresholds. It invokes wrap-all and merge-all, removes inner artifacts and independently runs block-v2-grouped-artifact-audit root-eight for every result.

python3 run-macos-comparison.py --threads 16 --runs 3
# Then, sequential one-run trials using the same fixture:
# --threads 8, 24, 24, 8, 8, 24; --runs 1; --fixture <first-run>/reference

Exact per-stage commands, binary hashes, fixture hashes, audit logs, the allocator patch and controller source are included in the downloadable evidence JSON. Raw Mac logs and root proof files remain under benchmark-results/block-v2-m5pro-20261003/ in the local repository.
