Consuming GPU recursive aggregation

8 November 2026 · base 3f1ebc0 · gpu-recursive-aggregation branch · Linux OpenCL / RTX 5080

Opt-in research profile. Complete N3/N4 latency remains unqualified. This round builds on the previous GPU implementation. It compares four-child groups with the existing optimized two-child groups using the same final source, native inputs, device, CPU identity policy, and fused witness/program-cache settings.

Implementation

  • grouped-v3 uses consuming registrations. GPU instruction buffers and their host schedule are released after the completed witness-trace fence, before lookup and quotient work. Public keys and verifiers remain available, and every recursive proof is freshly generated and independently verified.
  • Two persistent CPU workers retain source-bound numeric planning caches across requests. A dependency queue starts a parent as soon as both children are ready, preserving the original pairwise tree and odd tails. Four permits cover building, queued, and GPU-consuming programs together. GPU work stays on one caller thread.
  • Cancellation and worker panic handling retire in-flight preparation. Normal and error cleanup explicitly join the persistent workers before releasing reservations.
  • The consuming profile allows up to 524,288 rows. Existing profiles retain 262,144 rows. CPU identity with lookahead is required for this profile; the existing optional GPU identity route remains available separately.
  • Measured selection uses a versioned schema bound to source and physical device. Wider groups need at least a 10% warm-median gain over the optimized pair baseline. Graph partitioning preserves contiguous coverage and falls back to pairs or singletons when source row/compiler bounds exclude a contraction.

Memory and admission

The managed GPU cap remains 8 GiB. The consuming path fences and retires idle engine workspace before checking its backend phase bound against the current device epoch and live allocations. The original pre-session admission API and backend allocation, host, tree-storage, and physical-device checks remain in effect.

The consuming profile reserves 32 GiB simultaneously: 2 GiB for inputs, 8 GiB for the four source-program slots, 1 GiB for two compiler/identity auxiliaries, 20 GiB for the backend phase including its full 8 GiB retained-tree quota, and 1 GiB for outputs/reports. Source slots include programs under construction, avoiding a duplicate reservation for those same programs. Worker limits remain 32 GiB for N3 and 36 GiB for N4; external process and zero-swap guards are unchanged. Native input preparation keeps its separate existing 16 GiB allowance.

These enclosing reservations are conservative bounds, not measured RSS or a complete allocation-derived workflow memory proof. Source layout preflight checks rows and compiler storage; actual backend admission can still refuse an unfamiliar program before registration without retrying a failed proof. Dependency scheduling is within each tree; requests still run sequentially.

Reproduction

Use the existing exclusive guard through research/pq-ringct/tools/gpu_aggregation_campaign.py, with a unique revision and label for each attempt. Build the runner first and prepare a source-bound native bundle separately. The input fixture is deterministic; proof randomness remains fresh.

python3 research/pq-ringct/tools/gpu_aggregation_campaign.py driver \
  --revision NEW --label graph-pairs --command screen --case n4 \
  --bundle /absolute/native-bundle --device-uuid GPU-... -- \
  --profile grouped-v2 --group-width 2 --pipeline lookahead --identity cpu \
  --screen-family graph --first-leaf 4 --leaves 8 --repetitions 4
python3 research/pq-ringct/tools/gpu_aggregation_campaign.py driver \
  --revision NEW --label graph-four --command screen --case n4 \
  --bundle /absolute/native-bundle --device-uuid GPU-... -- \
  --profile grouped-v3 --group-width 4 --pipeline lookahead --identity cpu \
  --screen-family graph --first-leaf 4 --leaves 8 --repetitions 4

For SHAKE use --request 6 instead of the graph range. Generate source/device-bound costs with gpu_aggregation_select.py --pair BASELINE_RECORD CANDIDATE_RECORD --output SELECTION. A full run requires a complete native bundle, measured selection, and a new output path. This campaign has not exercised that complete acceptance path.
