# Original HashX native-to-outer handoff

This component-only research seam carries the same native attempt and original
claims through one preissued outer backend. It changes no production protocol,
native segmentation, cryptographic parameter, proof freshness policy, GPU
requirement, resource ceiling or complete-request dispatch gate. B051's complete
request refusal remains closed. A lifecycle owner cannot authenticate a leaf or
establish that its compiler implements the expected source; B owns those checks.

## Required order

1. B reserves its complete compiler, inputs, source/planning, retained outputs,
   independent verifier, reports and producer/caller owners. Every later owner
   must already be accounted before A derives the actual native PCS capacity.
2. `PendingNativeHashx::with_outer_bridge` admits a separate bridge claim before
   `prepare`. The claim is additive inside the original worker allowance. A
   detached ticket can outlive the pending/native owner, so native bookkeeping
   alone cannot back its independent inline state and retained `Rc` allocation.
3. A `prepare` fixes the actual original first phase and all nine successors.
   Before source planning or binding, B calls A041 `check_outer_request` with
   its own original request and ledger. Exact owner pointer and original ledger,
   source/bookkeeping/bridge claims, enabled-unbound state and the original
   unattempted current/successor/attachment checks must match. Two requests with
   the same geometry cannot pass this correlation check. It borrows owners and
   performs no allocation or admission. B then uses A039's checked numeric
   capacity with its original `FutureOuter` claims
   to construct the genuine `PreissuedOuterBackend`; no capacity is enlarged.
4. `PreparedNativeHashx::bind_outer_backend` checks the exact initial request,
   preparation, runtime, source successors, outputs, ledger and bookkeeping;
   core then ties the original backend to the private `Rc<Attempt>`. Both native
   and outer captured execution selections must still match the idle engine.
   B055 supplies the outer borrowing check without a new planner or capability.
5. `produce_for_outer(self, &ticket)` holds the immutable ticket borrow across
   all ten fresh native proofs, independent verifications and retirements. The
   default `produce` refuses every bridge-enabled owner, including one already
   bound. An enabled-unbound owner or absent/dropped/wrong ticket cannot enter
   native zero. No weak pointer, implicit fallback or retry after native work
   can bypass this state transition.
6. Every native child and attachment moves into B's retained child owners.
   `ticket.finish_native(completed)` consumes both only when all ten have moved.
   Core requires the same attempt, genuine successful terminal index9, exact
   startup/PCS/wrapper claims and fully retired native runtime. A validates the
   original request, ledger, preparation and separate verifier claims too.
7. B checks its exact compiled source. `RetiredHashxOuter::bind` consumes the
   original preissued backend using the actual Program/public/witness. It
   restores the original startup through the private OpenCL adapter, without
   exposing a new raw reservation accessor or readmitting bytes. The adapter
   uses the existing sealed startup internally. The original PCS/native wrapper
   claims remain opaque in the backend owner.
8. `PreparedHashxOuter::start` starts the original runtime after selection and
   ownership rechecks. B borrows `ActiveHashxOuter::session()` and `backend()` for
   real registration/proof and independent verification under B's preclaims.
   B must call `finish` even when setup/proof/output returns an error.
9. `finish` consumes that same Session before releasing any original support
   claim. It requires completed retirement, destroys the borrowed backend and
   returns `RetiredHashxOuterOriginals`, which has no Program/public/witness
   lifetime. Its allocation-free `check(request, ledger)` checks the original
   request and every claim plus actual zero-live/released retirement with a
   positive managed peak within8GiB. B separately requires genuine successful
   proof, independent verification and source authentication before acceptance.

## Memory and failure ownership

Managed8GiB/context4GiB, worker32GiB/native24GiB/process47GiB, host trees inside
the worker, zero swap and all row/thread limits remain unchanged. The outer
source's backend host scope must equal original PCS host bytes plus8GiB trees;
its managed/context declarations and source completeness flags are checked.
These numerical checks supplement genuine opaque ownership and cannot mint it.

The bridge claim adds complete core and research owners, results, error tuples,
runtime restoration/selection forwarding, moved/destructured native owners,
temporary helper arrays, ledger/claim/geometry/Rc frames, and independent Rc
backing. Multipliers are eight unless a larger explicit count applies, plus
bounded scalar/diagnostic slack. No inlining, move elision or tail-call credit
is assumed. B's original source/helper/planner claims are still additional;
the B055 selector may allocate and this bridge does not replace its storage.
The default native bookkeeping also charges the new `produce -> produce_inner`
owner/result/optional-ticket forwarding frames even with the bridge disabled.
All costs reduce the first immutable PCS assignment; no old larger capacity
can be reused after this source rotation.

A041 adds the full capacity helper census again for its separate cross-component
request check, plus all borrowed receiver/request/ledger and result forwarding
frames. This cost belongs to the bridge's original pre-native claim. B still
charges its own calling frames. The pure quota-boundary test automatically uses
the enlarged claim. Genuine same-geometry wrong-request/ledger refusal requires
the coordinator's pre-dispatch B producer qualification; no prepared owner is
fabricated for a mirrored pointer test.

The ticket owns its backend and retained attempt before its bridge claim.
Prepared/active/retired owners keep the actual runtime before the opaque backend
or scratch, and every original preparation/verifier/bookkeeping/bridge claim
survives payload destruction. Consuming refusals destroy complete owners; core
completion/refusal tuples retain originals until the research layer disposes
them. Runtime cleanup failures retain existing fail-stop behavior. Success
transitions check unchanged ledger snapshots; they do not admit or release
capacity. A finished runtime receipt alone never means the proof succeeded.

## Qualification still required

The authored pure tests exercise entry states, all-child transfer requirements,
exact bridge quota boundaries, wrong-ledger rejection, terminal claim release
and exact final segment geometry. They fabricate no genuine native attempt,
backend, proof, retirement or accepted leaf. Rustfmt source parsing is the only
execution performed by A. Coordinator release library/test builds and focused
tests remain required, followed by B's genuine producer, refusal/cleanup and
source-authenticated output qualification under the original guard.

No complete schedule fit, proof timing, workflow speedup or cryptographic
adoption claim follows from this seam. The prior full GPU guard refused fresh
memory admission before runtime/proof dispatch; this change does not relax it.
